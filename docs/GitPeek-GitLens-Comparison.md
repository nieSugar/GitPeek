# GitPeek 与 GitLens：资深用户视角对比

- 记录日期：2026-10-08（Asia/Shanghai）。
- GitPeek 基准：当前仓库 0.6.0 的源码、README 和实际功能范围。
- GitLens 基准：本次查阅的官方功能与权限文档；功能和套餐规则可能变化。
- 评估性质：按资深用户的需求作出的功能与交互设计判断，未进行两者实际操作计时、同机性能测试或长期使用验证。
- 本记录保存讨论结论，不自动转化为开发任务或修改现有版本范围。

## 当前选择

如果只能选一个长期主力工具，当前倾向 GitLens：代码调查经常从一行的作者信息深入到历史版本、相关文件、其他分支和引入行为变化的提交，更完整的追溯与搜索能力更适合这个过程。

如果日常需求主要是看代码、查文件历史、比较分支，且 Git 操作主要通过终端完成，则更偏向 GitPeek 的使用方式：操作意图明确，入口直接，中文界面便于理解。

## 场景对比

| 需求 | GitPeek 0.6.0 | GitLens | 当前判断 |
| --- | --- | --- | --- |
| 查看文件某次提交的改动 | 点击文件历史直接打开该文件的提交前后 Diff，支持重命名历史 | 文件历史、版本导航和比较选项更丰富 | GitPeek 适合快速查看 |
| 追查一段代码的演变 | 提供选区来源与演进历史；演进历史要求文件保存且无未提交修改，沿首父链追踪 | 提供选中行历史、整文件 blame 和逐版本导航 | 深入排查倾向 GitLens |
| 检索历史中的逻辑变化 | 按消息、作者、Hash 搜索，支持全部或当前分支范围 | 可按文件、具体代码变化、日期等检索 | GitLens 的检索范围更广 |
| 整理提交与团队评审 | 有分支操作、Cherry-pick、Stash；PR 集成和交互式 rebase 暂不在范围内 | 提供更完整的相关工作流，部分能力有套餐限制 | 倾向 GitLens |
| 私有仓库使用门槛 | 当前实现没有账号和订阅判断 | 基础 blame、Hover、版本导航免费；官方文档说明提交图在公开和本地仓库免费，私有仓库需要 Pro 或试用 | GitPeek 的门槛更直接 |

## GitPeek 值得保留的方向

- 围绕当前代码上下文组织操作，把“代码 → Commit → Diff”串得顺畅。
- 文件历史点击即进入对应 Diff，保留当前文件与历史路径之间的正确对应。
- 固定提交详情，连续查看多个 Diff 时保留上下文。
- 分支比较围绕共同祖先展开，帮助理解当前分支实际引入的改动。
- 保持中文入口和原生 VS Code 交互，减少选择、跳转与查找入口的负担。

## 需要保持清醒的判断

- “轻量”是设计方向，不能直接作为速度更快或稳定性更高的证据。
- GitLens 的基础代码追溯能力仍然免费，不能笼统地用“GitLens 收费”作为替代理由。
- VS Code 本身已有提交图、文件 Timeline 和行 blame，基础功能清单不足以构成持续的安装理由。
- GitPeek 的智能提交信息只依据文件路径和状态提供候选措辞，不理解完整 Diff 的业务意图。

## 后续讨论与验收重点

这些是候选评价标准，尚未立项：

1. 连续查看十几个提交时，用户始终清楚当前文件、版本和比较对象，打开 Diff 后上下文不丢失。
2. 同一项调查是否能减少点击、重复选择、入口查找和界面跳转。
3. 选区追溯和分支比较在重命名、多仓库、HEAD 变化等真实场景中是否准确，遇到能力边界时是否解释清楚。
4. 若要宣传性能或可靠性优势，应在相同仓库与环境下验证响应时间、资源占用和边界行为。
